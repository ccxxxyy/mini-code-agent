- **Weak-model control arm: the eval set DOES discriminate — the metric was saturated** — the benchmark's 48/48 and the ablation's 45/45 had both been read as "the eval set has no discriminating power", but that conclusion rested on a **single model**: an all-pass can mean the tasks are easy OR that this model is strong for these tasks, and the two call for opposite fixes. Same 16 tasks, same harness, same `--repeat 3`, only the model swapped for `qwen-turbo`: **pass@1 = 0.792, pass^3 = 0.750, 12/16 tasks fully passed, 2 censored runs**. 0.792 lands squarely in the informative band, and the failures are structured, not random — `three_bugs` 0/3, `multi_step_edit` 0/3, `write_unit_test` 0/3, `infer_convention` 2/3, three of which are the hardest tasks by design, so the difficulty ordering is valid. Three mechanisms that had been pinned at 1.0/1.0/0 and therefore never tested against reality all fired for the first time: (1) **pass^k's exponential decay became visible** — pass^3 and pass@1 are identical when everything passes, but 0.750 < 0.792 here, the gap coming from a 2/3 task, i.e. "unreliable, not incapable", which is the entire reason pass^k exists; (2) **censoring got real samples** — `write_unit_test`'s three failures are (22 iters, capped), (13 iters, not capped), (20 iters, capped), so two are censored observations and one is a genuine failure, and they must not be averaged together because a censored run would have kept burning tokens; (3) **the cost-denominator effect became measurable** — total / 16 tasks gives $0.0236 while total / 12 solved gives **$0.0315**, a 33% gap invisible in the baseline because 16/16 passed. Choosing the control model was itself an experiment: `qwen2.5-1.5b-instruct` fails even the easiest task (all-zero carries as little information as all-one) and `qwen3-8b` timed out, so `qwen-turbo` was picked for passing easy tasks and failing hard ones. Fixed en route: `runner.py` keyed results by task name only, so a second model **silently overwrote the first** — this actually destroyed three baseline files during probing and was recovered from the committed snapshot, proving the snapshot split earned its keep the same day; new `--results-dir` (default unchanged) plus `.gitignore` patterns for per-model live dirs. Cost figures are nominal — `qwen-turbo` is absent from `PRICE_TABLE` and falls back to the placeholder rate, so cross-model absolute costs are not comparable; only the 33% within-model denominator gap is a valid conclusion. Snapshot committed at `benchmarks/results-snapshot-qwen-turbo/`. - **Routine context compression had NO instrumentation, and the `compressions` metric counted something else** — preparing a live demo that shows a compression pass revealed that `-p --output-format stream-json` displays tool failure and self-correction fully but compression not at all, and the cause ran three layers deep. (1) `ContextSummaryStartEvent`/`DoneEvent` are documented as "Fork-style" and are emitted **only** from `core/subagent.py` for sub-agent context inheritance; routine conversation compression (`ContextManager.check_and_compress`) had zero hits for `emit`/`event_bus`/`Event` across `compressor.py` and `context.py`, violating the project's own rule that any implicit LLM call over ~1s needs a probe (compression IS an implicit LLM call when `llm_summarize` is on). (2) `MetricsCollector.compressions` was subscribed to that fork event, so **it could never count an actual compression**; all 48 benchmark runs showed 0, which looked correct (those tasks spawn no sub-agents) and hid the miswiring. (3) Worse, a unit test had pinned the bug: it emitted `ContextSummaryDoneEvent(duration_ms=48000.0)` and asserted `compressions == 1` — and that 48000ms is the real observed fork-summary duration, so the author knew it was a fork and only got the name wrong. New `ContextCompressedEvent` carries `before_tokens`/`after_tokens` rather than a compression ratio (ratio is the wrong metric — total tokens including the summary's own cost is the right one), `effective` to flag passes that did not reduce tokens (those are what open the compression circuit breaker, so dropping them hides the breaker's cause), `forced` to separate manual `/compact` from a threshold trigger, and `strategy` naming the cascade that actually ran (a pass that summarized and a pass that only slid the window mean different things) — for which `Compressor` gained a public `strategies` property so observers need not reach into a private field. `ContextManager.set_event_bus()` follows the existing `set_compressor()` injection pattern and is deliberately optional so headless callers keep working; the emit is wrapped because by that point the conversation has already been rewritten, and letting a subscriber's exception propagate would hand the caller a compressed conversation plus a False return. The metrics layer now keeps `compressions` and `context_forks` as separate counters with separate histograms, plus `compressions_ineffective` and `compressed_tokens_saved`. All three surfaces wired: TUI (`/trace` shows `ctx compacted 13455 -> 3051 tokens`, marked `(INEFFECTIVE)` when applicable), NDJSON (new `_wire_ndjson_bus` — compression is emitted by ContextManager, not a loop callback, so the existing callback wiring could not see it), and remote WebSocket (the browser previously saw a multi-second stall with no explanation — the same "looks hung" failure mode the fork-summary events were added to fix). End-to-end verified with `context_window = 4000`: two `context_compressed` lines, the second one `effective=False` at 3051 -> 3051, i.e. the circuit breaker's precursor now visible. 6 new tests, suite 1477->1483, coverage 86.93%->86.92%. See tech-notes §138. 常规上下文压缩零埋点，且 `compressions` 指标计的是别的东西——为准备"展示一次压缩"的现场 demo 时发现 `-p --output-format stream-json` 能完整展示工具失败与自纠，但压缩完全看不到，查下去有三层。(1) `ContextSummaryStartEvent`/`DoneEvent` 的文档写的是 "Fork-style"，且**只在** `core/subagent.py` 为子 Agent 继承上下文而发射；常规对话压缩（`ContextManager.check_and_compress`）在 `compressor.py` 与 `context.py` 里 `emit`/`event_bus`/`Event` 三个关键词全部零命中，违反项目自己定的"任何超过约 1 秒的隐式 LLM 调用都必须有埋点"（`llm_summarize` 开启时压缩正是隐式 LLM 调用）。(2) `MetricsCollector.compressions` 订阅的是那个 fork 事件，**永远数不到一次真正的压缩**；48 次评测里全是 0，看起来正常（那批任务不派生子 Agent），掩盖了接线错误。(3) 更糟的是一个单测把这个 bug 固化了：它 `emit(ContextSummaryDoneEvent(duration_ms=48000.0))` 然后断言 `compressions == 1`——而 48000ms 正是 fork 摘要的实测时长，说明写测试时就知道是 fork，只是名字用错了。新增 `ContextCompressedEvent`：带 `before_tokens`/`after_tokens` 而非压缩比（压缩比是错的指标，正确的是含摘要自身消耗的总 token）、`effective` 标记未降低 token 的压缩（正是它们打开压缩熔断器，丢掉会掩盖熔断原因）、`forced` 区分手动 `/compact` 与阈值触发、`strategy` 报出实际跑的级联（做了摘要与只滑窗口含义不同）——为此给 `Compressor` 加了公开 `strategies` 属性，避免观察方伸手进私有字段。`ContextManager.set_event_bus()` 沿用既有 `set_compressor()` 注入模式且故意可选，保证 headless 调用方继续可用；发射点包异常，因为走到那里时对话已被改写，让订阅者异常上抛会使调用方拿到"已压缩的对话 + False 返回值"。指标层把 `compressions` 与 `context_forks` 拆为独立计数器各带直方图，另加 `compressions_ineffective` 与 `compressed_tokens_saved`。三个出口全部接上：TUI（`/trace` 显示 `ctx compacted 13455 -> 3051 tokens`，无效时标 `(INEFFECTIVE)`）、NDJSON（新增 `_wire_ndjson_bus`——压缩由 ContextManager 发射而非循环回调，既有接线看不到）、远程 WebSocket（浏览器原本看到数秒卡顿却无任何解释，正是当初给 fork 摘要加事件所要修的"看起来卡死"故障模式）。端到端以 `context_window = 4000` 验证：两条 `context_compressed`，第二条 `effective=False`（3051 -> 3051），即熔断器前兆现在可见。6 个新测试，1477->1483，覆盖率 86.93%->86.92%。详见 tech-notes §138。

- **Compression ablation gained `--repeat`, per-task delta table and sign-flip detection** — `experiments/compression_ab.py` existed (arms: none / extractive / LLM summary) but had never produced data. Run as written (one run per cell, 15 runs) the token delta of a single arm **changed sign across tasks** — extractive saved 36% on `write_unit_test` and cost 9% more on `refactor_rename` — the same single-measurement trap that had just produced a false +12.7% elsewhere, so no conclusion was drawn from it. Added `--repeat` (aggregating medians and ranges via a `runs[]` shape matching `benchmarks/runner.py`) plus two anti-self-deception devices: a per-task delta table rather than only an aggregate median, and an automatic warning when an arm's delta has both signs across tasks ("the aggregate median is not a summary of a single effect"). Re-run at 5 tasks x 3 arms x 3 repeats = **45 runs, 45/45 passed**, so success rate again carries no information. Only **2 of 5 tasks are resolvable**, the criterion being whether iteration count is constant across repeats: on those two, **both compression strategies cost consistently MORE** (+5.6%/+7.0% extractive, +4.2%/+8.1% LLM) because `compressed_messages` is a median of 1 — a single compression pass per run, so the summary's own token cost has no later turns to amortize against. The other three tasks are explicitly left without a conclusion: at ~4,313 tokens per iteration, `write_unit_test` occasionally running 10 iterations instead of 6 adds 17k+ tokens against a ~1k compression effect, and its within-cell spread reaches 105% of the median — **within-cell spread exceeding between-arm delta means no conclusion**. Also recorded: the compression circuit breaker fired in the LLM arm under the forced 6,000-token window, so that arm partly degraded toward the no-compression arm, weakening the manipulation. Snapshot at `experiments/results-snapshot/`. - **Event-loop blocking comparison rebuilt; the previously reported "+12.7% scan cost" does not reproduce** — tech-notes §119 cited a script `verify_271_loop_block.py` that was **no longer in the repository**, leaving the project's most-quoted performance figure (1932.7ms -> 44.3ms, at a cost of ~12% scan time) as narrative with no way to re-run it. Rebuilt as `experiments/verify_loop_block.py`, with one deliberate design change: both arms alternate over **5 repeats** and report medians AND ranges instead of one measurement each. Result on 3,000 files / 70.4MB: **worst event-loop block 1,474.0ms -> 26.1ms (-98.2%)**, which reproduces the old -97.7%; but **scan time came out at a median of -3.0% with per-repeat deltas of [-19.9, -5.9, -8.8, -17.1, +8.5]%** — an interval straddling zero, so the cost is not measurable. The mechanism agrees: `_scan` is handed off to a thread **once for the whole walk**, so the switch is O(1) and cannot scale with 3,000 files; the old +12% was almost certainly a single-measurement artefact from cold-vs-warm page cache (measured here at ~1.9s cold vs ~0.33s warm, a 6x spread that swamps any real effect). An internal consistency check confirms the probe measures what it claims: in the blocking arm the block duration tracks the scan duration almost exactly (1474.0 vs 1473.6). §119's paragraph is now marked do-not-cite. The real output of the rebuild is the method, not the numbers: reporting a median without a range would have turned -3.0% into "slightly faster" instead of "not measurable". Also fixed: `report.py`'s bare `print(report)` raised `UnicodeEncodeError` on a default Windows GBK console (the report contains non-CP936 glyphs) and **lost the entire report**; stdout is now forced to UTF-8. - **Two zero-margin timing assertions removed from the metrics tests (~8% flake rate)** — a full-suite run failed on `test_collector_consumes_loop_ttft_end_to_end` and passed in isolation; looping it 12 times reproduced one failure, `assert 29.6 >= 30.0` against a nominal `MockLLM(delay=0.03)`. Root cause: `asyncio.sleep` is scheduled on the loop clock (`time.monotonic`) while TTFT is measured with `time.perf_counter` (`agent_loop.py:538,545`), and on Windows `monotonic` can be ~15.6ms coarse, so the sleep may return up to roughly one timer tick before `perf_counter` has advanced the nominal duration. The shortfall was initially mis-sized: isolating `asyncio.sleep(0.03)` over 200 iterations never undershot (min 30.128ms), so the tolerance was set at 3ms — 30 further runs still failed twice, surfacing a second assertion at `assert 40.4 >= 47.0` against a nominal 50ms, i.e. a **9.6ms** shortfall. Merely widening the tolerance was rejected: keeping 50ms with a 16ms tolerance yields a 34ms floor that an unrelated 34ms delay would also clear, destroying the assertion's discriminating power. `test_metrics.py` now passes 40 consecutive runs (2 failures in 30 before). Cost: ~0.3s of added runtime. ### Interface Freeze 接口冻结

The following ABCs and type aliases are now **stable**. Their method
signatures will not change without a major version bump.
以下 ABC 与类型别名现已**稳定**：不经历主版本号升级，其方法签名不会改变。

#### Tool (`tools/base.py`)

```python
class Tool(ABC):
    @property
    @abstractmethod
    def schema(self) -> ToolSchema: ...

    @abstractmethod
    async def execute(self, ctx: ToolContext, **kwargs: Any) -> ToolResult: ...
```

#### LLMProvider (`llm/base.py`)

```python
class LLMProvider(ABC):
    @abstractmethod
    async def stream(
        self, messages: list[dict[str, Any]],
        tools: list[dict[str, Any]] | None = None, **kwargs: Any
    ) -> AsyncIterator[StreamChunk]: ...

    @abstractmethod
    def count_tokens(self, text: str) -> int: ...

    @property
    @abstractmethod
    def context_window(self) -> int: ...
```

#### HookFn (`tools/hooks.py`)

```python
HookFn = Callable[[HookContext], Awaitable[HookResult]]
```

#### CompressionStrategy (`memory/compressor.py`)

```python
class CompressionStrategy(ABC):
    @abstractmethod
    async def compress(
        self, conversation: Conversation, target_tokens: int
    ) -> None: ...
```

### What "frozen" means 冻结的含义

- Method signatures (names, parameter types, return types) will not change 方法签名（名称、参数类型、返回类型）不会改变
- New **optional** parameters may be added with defaults 可以新增带默认值的**可选**参数
- New methods may be added to ABCs (existing ones won't change) ABC 可以新增方法（既有方法不变）
- Breaking changes require a major version bump (2.0.0) 破坏性变更必须升主版本号（2.0.0）
